# Нефункциональные требования

## 1. Безопасность

| ID | Название | Описание требования | Приоритет | Обоснование |
|----|----------|---------------------|-----------|-------------|
| **NFR-SEC-01** | Шифрование данных в транзите | Все данные, передаваемые между компонентами системы, должны шифроваться с использованием TLS 1.3 | Must Have | Защита от перехвата данных при передаче, соответствие требованиям регуляторов |
| **NFR-SEC-02** | Шифрование данных в покое | Персональные данные и история обращений должны храниться в зашифрованном виде (AES-256) | Must Have | Защита от утечек при компрометации хранилища, выполнение требований 152-ФЗ |
| **NFR-SEC-03** | Аутентификация пользователей | Доступ к системе только через корпоративный SSO (OAuth 2.0 / OpenID Connect) | Must Have | Исключение несанкционированного доступа, единое управление учетными записями |
| **NFR-SEC-04** | Двухфакторная аутентификация | Операторы и администраторы должны использовать 2FA при входе в систему | Should Have | Дополнительный уровень защиты от компрометации учетных записей |
| **NFR-SEC-05** | Ролевая модель доступа | Разграничение прав доступа для операторов и администраторов | Must Have | Предотвращение несанкционированных действий, соблюдение принципа минимальных привилегий |
| **NFR-SEC-06** | Аудируемость действий | Логирование всех действий пользователей с возможностью расследования инцидентов | Must Have | Обеспечение неотказуемости, возможность расследования инцидентов |
| **NFR-SEC-07** | Защита от инъекций | Валидация и санитизация всех входных данных для предотвращения SQL-инъекций и XSS-атак | Must Have | Предотвращение компрометации системы через пользовательский ввод |
| **NFR-SEC-08** | Анонимизация данных | Персональные данные должны автоматически анонимизироваться при передаче в ML-модели для обучения | Must Have | Соблюдение законодательства о персональных данных, снижение рисков утечек |
| **NFR-SEC-09** | Соответствие 152-ФЗ | Хранение данных только на серверах, расположенных на территории РФ | Must Have | Выполнение требований российского законодательства |
| **NFR-SEC-10** | Регулярное тестирование на проникновение | Проведение пентестов не реже 1 раза в квартал | Should Have | Выявление уязвимостей до их эксплуатации злоумышленниками |
| **NFR-SEC-11** | Защита от DDoS | Наличие механизмов защиты от распределенных атак на уровне инфраструктуры | Should Have | Обеспечение доступности сервиса при целенаправленных атаках |
| **NFR-SEC-12** | Управление секретами | Хранение паролей и API-ключей в защищенном хранилище (HashiCorp Vault / аналоги) | Must Have | Предотвращение утечек чувствительных данных из кода и конфигураций |

## 2. Производительность

| ID | Название | Описание требования | Приоритет | Обоснование |
|----|----------|---------------------|-----------|-------------|
| **NFR-PERF-01** | Время ответа API | Среднее время ответа API (p95) на запросы от интерфейса оператора не должно превышать 500 мс | Must Have | Операторы не должны испытывать задержек при работе, влияющих на скорость обслуживания |
| **NFR-PERF-02** | Время генерации рекомендаций | Время от получения сообщения до выдачи рекомендаций оператору не должно превышать 500 мс | Must Have | Рекомендации должны поступать оператору до того, как он начнет печатать ответ |
| **NFR-PERF-03** | Время поиска по уставу | Максимальное время поиска релевантных пунктов в уставе не должно превышать 400 мс | Must Have | Оператор должен получать информацию из устава мгновенно, без пауз в диалоге |
| **NFR-PERF-04** | Пропускная способность | Количество обрабатываемых сообщений в секунду на один инстанс должно быть не менее 100 | Must Have | Обеспечение работы в пиковые нагрузки без деградации производительности |
| **NFR-PERF-05** | Время загрузки интерфейса | Время полной загрузки интерфейса оператора не должно превышать 3 секунд | Should Have | Быстрый старт работы оператора, снижение времени простоя |
| **NFR-PERF-06** | Время индексации устава | Время индексации документа устава объемом до 500 страниц не должно превышать 5 минут | Should Have | Администратор должен получать обновленный устав в работу без длительного ожидания |
| **NFR-PERF-07** | Параллельная обработка | Количество одновременных диалогов, обрабатываемых без деградации производительности, должно быть не менее 1000 | Must Have | Обеспечение работы крупных контакт-центров без потери качества |
| **NFR-PERF-08** | Использование ресурсов | Пиковая нагрузка на CPU не должна превышать 75% при штатной работе | Should Have | Обеспечение запаса производительности для пиковых нагрузок |
| **NFR-PERF-09** | Использование памяти | Пиковая нагрузка на RAM не должна превышать 80% при штатной работе | Should Have | Предотвращение исчерпания памяти и связанных с этим сбоев |
| **NFR-PERF-10** | Время восстановления после сбоя | Максимальное время восстановления работоспособности после критического сбоя не должно превышать 15 минут | Should Have | Минимизация простоев и их влияния на бизнес-процессы |

## 3. Надежность

| ID | Название | Описание требования | Приоритет | Обоснование |
|----|----------|---------------------|-----------|-------------|
| **NFR-REL-01** | Доступность системы | Гарантированная доступность системы для пользователей должна составлять не менее 99.5% в версии 1.0 и 99.9% в версии 2.0 | Must Have | Обеспечение непрерывности бизнес-процессов поддержки клиентов |
| **NFR-REL-02** | Отказоустойчивость | Система должна продолжать работу при отказе одного из компонентов (N+1 резервирование) | Must Have | Исключение единой точки отказа, обеспечение непрерывности сервиса |
| **NFR-REL-03** | Резервное копирование | Автоматическое резервное копирование данных должно выполняться не реже 1 раза в сутки | Must Have | Возможность восстановления данных при сбоях и инцидентах |
| **NFR-REL-04** | Восстанавливаемость данных | Гарантированное восстановление данных из резервной копии должно занимать не более 4 часов | Must Have | Минимизация потерь при критических сбоях |
| **NFR-REL-05** | Graceful degradation | При недоступности ML-компонентов система должна продолжать работу с базовым функционалом | Should Have | Обеспечение минимальной работоспособности даже при частичных отказах |
| **NFR-REL-06** | Обработка ошибок | Система должна корректно обрабатывать ошибки и возвращать понятные сообщения | Must Have | Упрощение диагностики проблем, улучшение пользовательского опыта |
| **NFR-REL-07** | Ретриты и таймауты | Наличие механизмов повторных попыток (3 попытки) и таймаутов (5 сек) при интеграции с внешними сервисами | Must Have | Повышение отказоустойчивости при временных проблемах внешних систем |
| **NFR-REL-08** | Мониторинг здоровья | Автоматический мониторинг состояния всех компонентов системы с проверкой каждые 30 секунд | Must Have | Своевременное обнаружение проблем и реагирование на них |
| **NFR-REL-09** | Автоматическое переключение | Автоматическое переключение на резервный компонент при отказе основного должно выполняться менее чем за 1 минуту | Should Have | Минимизация времени простоя при отказах |
| **NFR-REL-10** | Среднее время наработки на отказ | MTBF (Mean Time Between Failures) должен составлять не менее 720 часов | Should Have | Обеспечение стабильной работы системы без сбоев |

## 4. Емкость

| ID | Название | Описание требования | Приоритет | Обоснование |
|----|----------|---------------------|-----------|-------------|
| **NFR-CAP-01** | Количество операторов | Система должна поддерживать одновременно работающих операторов: версия 1.0 — 50, версия 1.5 — 200, версия 2.0 — 500+ | Must Have | Обеспечение роста бизнеса без необходимости замены системы |
| **NFR-CAP-02** | Количество одновременных диалогов | Система должна поддерживать активные диалоги: версия 1.0 — 200, версия 2.0 — 2000+ | Must Have | Обеспечение работы в пиковые нагрузки без деградации |
| **NFR-CAP-03** | Объем хранимой истории | Система должна хранить историю обращений не менее 3 лет (объемом более 10 млн диалогов) | Must Have | Соответствие требованиям к хранению данных, возможность анализа многолетней динамики |
| **NFR-CAP-04** | Объем документов устава | Система должна поддерживать загрузку документов устава объемом до 1000 страниц и до 50 МБ | Must Have | Обеспечение работы с реальными документами организаций |
| **NFR-CAP-05** | Количество документов устава | Система должна поддерживать неограниченное количество одновременно активных версий устава | Should Have | Возможность работы с несколькими брендами и продуктами |
| **NFR-CAP-06** | Пропускная способность API | API системы должно выдерживать нагрузку более 500 запросов в секунду | Should Have | Обеспечение работы при интенсивном использовании и интеграциях |
| **NFR-CAP-07** | Масштабируемость хранения | Хранилище данных должно поддерживать горизонтальное масштабирование (шардинг) | Must Have | Возможность увеличения объема данных без потери производительности |
| **NFR-CAP-08** | Масштабируемость вычислений | Вычислительные мощности должны поддерживать горизонтальное масштабирование (автоскейлинг) | Must Have | Адаптация к пиковым нагрузкам без ручного вмешательства |
| **NFR-CAP-09** | Скорость роста данных | Прогнозируемый ежегодный рост объема данных не должен превышать 30% | Should Have | Возможность планирования ресурсов и бюджета на хранение |

## 5. Наблюдаемость

| ID | Название | Описание требования | Приоритет | Обоснование |
|----|----------|---------------------|-----------|-------------|
| **NFR-OBS-01** | Логирование | Централизованный сбор логов от всех компонентов системы с хранением не менее 30 дней | Must Have | Возможность диагностики проблем и расследования инцидентов |
| **NFR-OBS-02** | Мониторинг метрик | Сбор ключевых метрик производительности (latency, throughput, error rate) не менее 20 метрик | Must Have | Отслеживание состояния системы в реальном времени |
| **NFR-OBS-03** | Дашборды | Наличие дашбордов для визуализации состояния системы и бизнес-метрик (не менее 5 дашбордов) | Must Have | Быстрая оценка состояния системы без анализа сырых данных |
| **NFR-OBS-04** | Алертинг | Настройка оповещений при выходе метрик за допустимые границы (не менее 10 алертов) | Must Have | Своевременное реагирование на проблемы до их влияния на пользователей |
| **NFR-OBS-05** | Трассировка запросов | Возможность отслеживания полного пути запроса через все компоненты (distributed tracing) | Should Have | Диагностика сложных проблем во взаимодействии микросервисов |
| **NFR-OBS-06** | Бизнес-метрики | Сбор и визуализация бизнес-метрик (CSAT, Acceptance Rate, AHT) не менее 15 метрик | Must Have | Оценка эффективности системы для бизнеса |
| **NFR-OBS-07** | Мониторинг использования ресурсов | Отслеживание использования CPU, RAM, диска, сети в реальном времени | Must Have | Планирование мощностей, предотвращение исчерпания ресурсов |
| **NFR-OBS-08** | Мониторинг доступности | Автоматическая проверка доступности ключевых эндпоинтов каждые 5 минут | Must Have | Обнаружение проблем с доступностью до жалоб пользователей |
| **NFR-OBS-09** | Аудит действий | Отдельное логирование действий пользователей с хранением более 1 года | Must Have | Обеспечение compliance, возможность расследования инцидентов |
| **NFR-OBS-10** | Интеграция с SIEM | Возможность передачи логов в SIEM-системы в стандартных форматах | Could Have | Централизованный мониторинг безопасности в крупных организациях |

## 6. Удобство использования

| ID | Название | Описание требования | Приоритет | Обоснование |
|----|----------|---------------------|-----------|-------------|
| **NFR-USA-01** | Интуитивность интерфейса | Интерфейс должен быть понятным для операторов без длительного обучения (тестирование с 5 пользователями) | Must Have | Снижение затрат на обучение, быстрый вывод новых сотрудников на линию |
| **NFR-USA-02** | Скорость обучения | Время освоения базовых функций новым оператором не должно превышать 2 часов | Must Have | Минимизация простоев новых сотрудников |
| **NFR-USA-03** | Доступность интерфейса | Соответствие стандартам доступности WCAG 2.1 (уровень AA) для людей с ограниченными возможностями | Should Have | Обеспечение равного доступа к работе для всех сотрудников |
| **NFR-USA-04** | Локализация | Интерфейс на русском языке с поддержкой i18n для добавления других языков | Must Have | Соответствие языку пользователей, возможность масштабирования |
| **NFR-USA-05** | Адаптивный дизайн | Корректное отображение на различных разрешениях экрана (1920x1080, 1366x768) | Must Have | Обеспечение работы на разных рабочих местах |
| **NFR-USA-06** | Поддержка горячих клавиш | Наличие горячих клавиш для часто используемых действий (не менее 10) | Could Have | Повышение скорости работы опытных операторов |
| **NFR-USA-07** | Понятность сообщений об ошибках | Сообщения об ошибках должны быть на русском языке, понятны пользователю и содержать рекомендации по действиям | Must Have | Снижение нагрузки на техническую поддержку |
| **NFR-USA-08** | Наличие подсказок | Контекстные подсказки (tooltips) и onboarding для новых пользователей | Should Have | Ускорение обучения, снижение количества ошибок |
| **NFR-USA-09** | Персонализация интерфейса | Возможность настройки отображения элементов интерфейса под предпочтения оператора | Could Have | Повышение комфорта работы, учет индивидуальных предпочтений |
| **NFR-USA-10** | Скорость отклика интерфейса | Визуальная обратная связь на действия пользователя должна появляться менее чем за 100 мс | Should Have | Обеспечение ощущения отзывчивости системы |

## 7. Поддерживаемость

|----|----------|---------------------|-----------|-------------|
| **NFR-MNT-01** | Модульность архитектуры | Система должна состоять из слабосвязанных модулей с четкими интерфейсами (микросервисная архитектура) | Must Have | Возможность независимой разработки, тестирования и развертывания компонентов |
| **NFR-MNT-02** | Документирование | Наличие актуальной технической документации (OpenAPI, README, ADR) | Must Have | Обеспечение возможности поддержки системы разными командами |
| **NFR-MNT-03** | Код-стайл | Единый стиль кодирования с возможностью автоматической проверки (PEP8, ESLint, Prettier) | Should Have | Упрощение чтения и поддержки кода |
| **NFR-MNT-04** | Тестируемость | Возможность автоматического тестирования отдельных модулей и системы в целом с покрытием тестами не менее 70% | Must Have | Обеспечение качества при внесении изменений |
| **NFR-MNT-05** | CI/CD | Наличие пайплайнов непрерывной интеграции и доставки (GitLab CI / GitHub Actions) | Must Have | Автоматизация сборки, тестирования и развертывания |
| **NFR-MNT-06** | Версионирование | Четкое версионирование API и компонентов системы по Semantic Versioning | Must Have | Управление изменениями, обратная совместимость |
| **NFR-MNT-07** | Обратная совместимость | API должен сохранять обратную совместимость в рамках мажорной версии (без breaking changes) | Must Have | Защита клиентов от поломок при обновлениях |
| **NFR-MNT-08** | Время развертывания | Время развертывания новой версии системы не должно превышать 30 минут | Should Have | Возможность частых релизов без длительных простоев |
| **NFR-MNT-09** | Откат версий | Возможность быстрого отката к предыдущей версии менее чем за 15 минут | Must Have | Минимизация последствий неудачных релизов |
| **NFR-MNT-10** | Конфигурируемость | Вынесение параметров работы в конфигурационные файлы без изменения кода (12-factor app) | Must Have | Адаптация под разные окружения без пересборки |

## 8. Совместимость

| ID | Название | Описание требования | Приоритет | Обоснование |
|----|----------|---------------------|-----------|-------------|
| **NFR-COMP-01** | Поддержка браузеров | Поддержка актуальных версий Chrome, Firefox, Safari, Edge (последние 2 версии) | Must Have | Обеспечение работы на всех распространенных рабочих местах |
| **NFR-COMP-02** | Интеграция с CRM | Возможность интеграции с популярными CRM через REST API | Must Have | Бесшовная интеграция в существующую инфраструктуру клиента |
| **NFR-COMP-03** | Интеграция с системами чатов | Поддержка интеграции с веб-чатами и мессенджерами через WebSocket и REST API | Must Have | Работа с существующими каналами коммуникации |
| **NFR-COMP-04** | Экспорт данных | Возможность экспорта данных в форматах JSON, CSV, Excel | Should Have | Предоставление данных клиентам для их аналитики |
| **NFR-COMP-05** | Импорт данных | Поддержка импорта исторических данных из внешних систем в форматах CSV, JSON | Should Have | Перенос истории при переходе на систему |
