Проектирование ERD

Примечание: В базе данных всего 15 сущностей, но все схемы представлены для 11 основных. Это сделано для более простого восприятия структуры БД.

Уровень 1 — Концептуальная модель​

Концептуальная модель показывает основные сущности системы и связи между ними на высоком уровне абстракции, без детализации атрибутов.

Описание сущностей концептуальной модели​

№СущностьНазначениеКлючевая связьОсновные атрибуты
1Пользователь (users)Операторы, администраторы, супервизоры системыВедёт сессии, получает рекомендацииID, имя, email, активен
2Роль пользователя (user_roles)Определяет права доступаПринадлежит пользователюID пользователя, название роли
3Клиент (clients)Клиенты, обращающиеся в поддержкуУчаствует в сессияхID, email, телефон, сегмент
4Сессия чата (chat_sessions)Контейнер для одного диалогаСодержит сообщения, генерирует рекомендацииID, статус, приоритет, оценка
5Сообщение (chat_messages)Единица диалогаПринадлежит сессии, анализируетсяID, текст, отправитель, время
6Анализ тональности (sentiment_analysis)Результат NLP-анализаПривязан к сообщениюID, тональность, срочность, эмоции
7Рекомендация (recommendations)Подсказки AI для оператораПривязана к сессии и операторуID, текст, тип, приоритет
8Устав организации (company_charter)Правила общения компанииСоздаётся админомID, код, текст, категория
9База знаний (knowledge_base)Статьи FAQ для клиентовСоздаётся админомID, заголовок, содержание, теги
10Шаблон ответа (response_templates)Готовые фразы для операторовСоздаётся админомID, код, текст, категория
11Триггерное слово (trigger_keywords)Ключевые слова для автоматизацииНастраивается админомID, слово, действие, приоритет

Обоснование проектных решений​

БД может показаться избыточной (поля типа timestamp и прочие атрибуты, не нужные в первую очередь), но это сделано для:

  • Упрощения работы аналитики — выявления влияния адаптивного помощника на получение валидного опыта клиентом
  • Выявления «виновного» в отсутствии такого опыта (оператор / система)
  • Удобного масштабирования при необходимости

Обоснование использования JSONB:

АспектПояснение
Гибкость схемыУ отдельной таблицы плохая гибкость (каждое новое поле требует ALTER TABLE и миграции). У JSON новые поля добавляются без изменения схемы
Разные каналыОтдельная таблица требует множества NULL-полей или отдельных таблиц под каждый канал. JSON использует единую структуру, поля зависят от канала
ГромоздкостьВместо JSON можно было сделать отдельные сущности, что потребовало бы создания дополнительных таблиц

Выводы по моделям данных​

Разработанные модели данных обеспечивают:

  • Целостность и согласованность данных через внешние ключи
  • Производительность запросов через индексы
  • Гибкость схемы через JSONB-поля
  • Масштабируемость через партиционирование и денормализацию
