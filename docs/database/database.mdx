# Модель данных и технологии хранения

## Определение сущностей

### Пользователи системы (`users`)

Хранит информацию обо всех пользователях системы (операторы, администраторы, супервизоры).

| Атрибут | Тип | Null? | Описание |
|---------|-----|-------|----------|
| `id_user` | SERIAL | NOT NULL | Уникальный идентификатор пользователя |
| `username` | VARCHAR(100) | NOT NULL | Логин пользователя |
| `email` | VARCHAR(150) | NOT NULL | Email для аутентификации |
| `password_hash` | VARCHAR(255) | NOT NULL | Хеш пароля |
| `first_name` | VARCHAR(100) | NOT NULL | Имя |
| `last_name` | VARCHAR(100) | NOT NULL | Фамилия |
| `middle_name` | VARCHAR(100) | NULL | Отчество |
| `full_name` | VARCHAR(300) | STORED | Полное имя (генерируется автоматически) |
| `updated_at` | TIMESTAMP | NOT NULL | Дата обновления записи |

**Акторы:** Админ (создание/редактирование), Оператор (чтение своего профиля), Система (автоматическое обновление)

## Выбор технологий хранения

### Объём данных

| Сущность | Прогнозируемый объём |
|----------|---------------------|
| `clients` | 100 тыс - 1 млн |
| `chat_messages` | 50-100 млн/год |
| `chat_sessions` | 1-2 млн/год |
| `sentiment_analysis` | 50-100 млн/год |
| `recommendations` | 5-10 млн/год |
| `audit_log` | 10-20 млн/год |
| `knowledge_base` | 1-5 тыс |
| `users` + `user_roles` | 100-500 |

### Паттерны записи и чтения

| Сущность | Паттерн | Характеристика |
|----------|---------|----------------|
| `clients` | OLTP | 70% SELECT, 20% INSERT, 10% UPDATE |
| `chat_messages` | OLTP + Streaming | 90% INSERT, 10% SELECT |
| `chat_sessions` | OLTP | 60% INSERT, 30% UPDATE, 10% SELECT |
| `sentiment_analysis` | Event Streaming | 99% INSERT, 1% SELECT |
| `recommendations` | OLTP | 50% INSERT, 50% UPDATE |
| `knowledge_base` | OLAP | 95% SELECT, 5% UPDATE |
| `audit_log` | Event Streaming | 100% INSERT |
| `daily_stats` | OLAP | 100% INSERT (агрегация) |

### Требования к консистентности

| Сущность | Требование | Обоснование |
|----------|------------|-------------|
| `clients` | Strong | Данные клиента должны быть точными |
| `users`, `user_roles` | Strong | Права доступа не могут быть рассинхронизированы |
| `chat_messages`, `chat_sessions` | Strong | Клиент должен видеть все сообщения |
| `recommendations` | Eventual | Не критично, если рекомендация появится на 0.5 сек позже |
| `sentiment_analysis` | Eventual | Может обработаться асинхронно |
| `daily_stats`, `audit_log` | Eventual | Отчёты и логи не требуют real-time |

### Требования к поиску и запросам

| Тип запроса | Инструмент |
|-------------|------------|
| Поиск по ID | B-tree index |
| Поиск по email/телефону | B-tree уникальный индекс |
| Поиск по времени | B-tree на `timestamp` |
| Полнотекстовый поиск | GIN index + `to_tsvector` |
| Поиск по тегам | GIN index на массив |
| Поиск по JSONB | GIN index на JSONB |
| Агрегация | TimescaleDB / ClickHouse |

### Итоговое решение по технологиям

| Сущность | Решение |
|----------|---------|
| `clients`, `users`, `chat_sessions` | **PostgreSQL** (OLTP, строгая консистентность) |
| `chat_messages` | **PostgreSQL + партиционирование** (высокая интенсивность записи) |
| `sentiment_analysis`, `recommendations` | **PostgreSQL** (асинхронная запись) |
| `company_charter`, `response_templates`, `trigger_keywords` | **PostgreSQL + Redis** (кеширование) |
| `knowledge_base` | **PostgreSQL + GIN** (полнотекстовый поиск) |
| `audit_log` | **ClickHouse** или **TimescaleDB** (аналитические, только вставка) |
| `daily_stats`, `operator_stats` | **TimescaleDB** (гипертаблицы для агрегации) |

### Обоснование выбора PostgreSQL

```text
1. Поддержка JSONB для гибких метаданных
2. Полнотекстовый поиск (GIN индексы, to_tsvector)
3. Партиционирование для больших таблиц (chat_messages)
4. Надёжность и соответствие требованиям к консистентности
5. Open-source, низкая стоимость владения
