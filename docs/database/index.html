Модель данных и технологии хранения

Определение сущностей​

Пользователи системы (users)​

Хранит информацию обо всех пользователях системы (операторы, администраторы, супервизоры).

АтрибутТипNull?Описание
id_userSERIALNOT NULLУникальный идентификатор пользователя
usernameVARCHAR(100)NOT NULLЛогин пользователя
emailVARCHAR(150)NOT NULLEmail для аутентификации
password_hashVARCHAR(255)NOT NULLХеш пароля
first_nameVARCHAR(100)NOT NULLИмя
last_nameVARCHAR(100)NOT NULLФамилия
middle_nameVARCHAR(100)NULLОтчество
full_nameVARCHAR(300)STOREDПолное имя (генерируется автоматически)
updated_atTIMESTAMPNOT NULLДата обновления записи

Акторы: Админ (создание/редактирование), Оператор (чтение своего профиля), Система (автоматическое обновление)

Выбор технологий хранения​

Объём данных​

СущностьПрогнозируемый объём
clients100 тыс - 1 млн
chat_messages50-100 млн/год
chat_sessions1-2 млн/год
sentiment_analysis50-100 млн/год
recommendations5-10 млн/год
audit_log10-20 млн/год
knowledge_base1-5 тыс
users + user_roles100-500

Паттерны записи и чтения​

СущностьПаттернХарактеристика
clientsOLTP70% SELECT, 20% INSERT, 10% UPDATE
chat_messagesOLTP + Streaming90% INSERT, 10% SELECT
chat_sessionsOLTP60% INSERT, 30% UPDATE, 10% SELECT
sentiment_analysisEvent Streaming99% INSERT, 1% SELECT
recommendationsOLTP50% INSERT, 50% UPDATE
knowledge_baseOLAP95% SELECT, 5% UPDATE
audit_logEvent Streaming100% INSERT
daily_statsOLAP100% INSERT (агрегация)

Требования к консистентности​

СущностьТребованиеОбоснование
clientsStrongДанные клиента должны быть точными
users, user_rolesStrongПрава доступа не могут быть рассинхронизированы
chat_messages, chat_sessionsStrongКлиент должен видеть все сообщения
recommendationsEventualНе критично, если рекомендация появится на 0.5 сек позже
sentiment_analysisEventualМожет обработаться асинхронно
daily_stats, audit_logEventualОтчёты и логи не требуют real-time

Требования к поиску и запросам​

Тип запросаИнструмент
Поиск по IDB-tree index
Поиск по email/телефонуB-tree уникальный индекс
Поиск по времениB-tree на timestamp
Полнотекстовый поискGIN index + to_tsvector
Поиск по тегамGIN index на массив
Поиск по JSONBGIN index на JSONB
АгрегацияTimescaleDB / ClickHouse

Итоговое решение по технологиям​

СущностьРешение
clients, users, chat_sessionsPostgreSQL (OLTP, строгая консистентность)
chat_messagesPostgreSQL + партиционирование (высокая интенсивность записи)
sentiment_analysis, recommendationsPostgreSQL (асинхронная запись)
company_charter, response_templates, trigger_keywordsPostgreSQL + Redis (кеширование)
knowledge_basePostgreSQL + GIN (полнотекстовый поиск)
audit_logClickHouse или TimescaleDB (аналитические, только вставка)
daily_stats, operator_statsTimescaleDB (гипертаблицы для агрегации)

Обоснование выбора PostgreSQL​

1. Поддержка JSONB для гибких метаданных
2. Полнотекстовый поиск (GIN индексы, to_tsvector)
3. Партиционирование для больших таблиц (chat_messages)
4. Надёжность и соответствие требованиям к консистентности
5. Open-source, низкая стоимость владения
