Примечание по проектированию БД:
БД может показаться избыточной (поля типа timestamp и прочие атрибуты, не нужные в первую очередь), но это сделано для заметного упрощения работы аналитики (выявления влияния адаптивного помощника на получение валидного опыта клиентом, а также выявления "виновного" в отсутствии такого опыта — оператор/система), а также для удобного масштабирования (при необходимости).

Обоснование использования JSONB:
Я понимаю, что атрибуты типа JSONB могут стать слабым местом в БД при определённой нагрузке, однако они были использованы для гибкости и уменьшения громоздкости (вместо JSON можно было сделать отдельные сущности, что потребовало бы создания отдельных таблиц). Гибкость схемы: у отдельной таблицы плохая гибкость (каждое новое поле требует ALTER TABLE и миграции), у JSON же новые поля добавляются без изменения схемы. Кроме того, отдельная таблица требует множества NULL-полей или отдельных таблиц под каждый канал, а JSON позволяет использовать единую структуру, где поля зависят от канала.

2. Выбор технологий хранения​

Анализ требований к системе​

Исходные требования:

  • Хранение информации о клиентах, операторах и сессиях чата
  • Быстрое чтение профиля сессии по ID
  • Обновление данных в реальном времени (сообщения, статусы)
  • Генерация рекомендаций для оператора (мгновенно)
  • Запуск аналитических отчетов (ежедневно)
  • Полнотекстовый поиск по сообщениям и базе знаний
  • Хранение аудита действий
  • Поиск и идентификация клиентов по email/телефону/full_name
  • Аналитика по клиентам (LTV, сегментация)

Поиск по клиентам"Найди всех VIP клиентов"B-tree на segment, GIN на tags
Агрегация"Средняя тональность за день"TimescaleDB / ClickHouse
Поиск по JSONB"Найди сообщения с device_type = 'mobile'"GIN index на JSONB
Поиск по тегам"Сессии с тегом 'urgent'"GIN index на array
