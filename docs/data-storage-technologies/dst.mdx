### 1.2 Сводная таблица акторов

| Актор | Создает | Читает | Обновляет | Удаляет |
|-------|---------|--------|-----------|---------|
| **Клиент** | chat_sessions, chat_messages | knowledge_base | - | - |
| **Оператор** | chat_messages | chat_sessions, chat_messages, recommendations, response_templates, company_charter, clients | recommendations (apply/dismiss), chat_sessions (status) | - |
| **Админ** | users, user_roles, clients, company_charter, response_templates, trigger_keywords, knowledge_base | всё | всё | users, user_roles, clients |
| **Система** | sentiment_analysis, recommendations, daily_stats, operator_stats, audit_log | всё | clients (статистика), recommendations (expires_at), chat_sessions (status) | recommendations (TTL) |
| **Аналитик** | - | daily_stats, operator_stats, sentiment_analysis, audit_log, clients | - | - |

> **Примечание по проектированию БД:**  
> БД может показаться избыточной (поля типа timestamp и прочие атрибуты, не нужные в первую очередь), но это сделано для заметного упрощения работы аналитики (выявления влияния адаптивного помощника на получение валидного опыта клиентом, а также выявления "виновного" в отсутствии такого опыта — оператор/система), а также для удобного масштабирования (при необходимости).  
>
> **Обоснование использования JSONB:**  
> Я понимаю, что атрибуты типа JSONB могут стать слабым местом в БД при определённой нагрузке, однако они были использованы для гибкости и уменьшения громоздкости (вместо JSON можно было сделать отдельные сущности, что потребовало бы создания отдельных таблиц). Гибкость схемы: у отдельной таблицы плохая гибкость (каждое новое поле требует ALTER TABLE и миграции), у JSON же новые поля добавляются без изменения схемы. Кроме того, отдельная таблица требует множества NULL-полей или отдельных таблиц под каждый канал, а JSON позволяет использовать единую структуру, где поля зависят от канала.

## 2. Выбор технологий хранения

### Анализ требований к системе

**Исходные требования:**
- Хранение информации о клиентах, операторах и сессиях чата
- Быстрое чтение профиля сессии по ID
- Обновление данных в реальном времени (сообщения, статусы)
- Генерация рекомендаций для оператора (мгновенно)
- Запуск аналитических отчетов (ежедневно)
- Полнотекстовый поиск по сообщениям и базе знаний
- Хранение аудита действий
- **Поиск и идентификация клиентов по email/телефону/full_name**
- **Аналитика по клиентам (LTV, сегментация)**

---

### 2.1 Технологии хранения по шагам

#### Шаг 1. Объём данных

| Сущность | Прогнозируемый объём | Обоснование |
|----------|---------------------|-------------|
| **clients** | 100 тыс - 1 млн | Уникальные клиенты, обращающиеся в поддержку |
| **chat_messages** | 50-100 млн/год | 10 000 сообщений/день × 365 дней |
| **chat_sessions** | 1-2 млн/год | 500 сессий/день × 365 дней |
| **sentiment_analysis** | 50-100 млн/год | 1:1 с сообщениями |
| **recommendations** | 5-10 млн/год | 10 рекомендаций/сессию |
| **audit_log** | 10-20 млн/год | 100 действий/день × 365 |
| **knowledge_base** | 1-5 тыс | Статические статьи |
| **company_charter** | 50-200 | Статические правила |
| **users + roles** | 100-500 | Операторы и админы |

---

#### Шаг 2. Паттерны записи и чтения

| Сущность | Паттерн | Характеристика |
|----------|---------|----------------|
| **clients** | OLTP (чтение + редкое обновление) | 70% SELECT, 20% INSERT (новые клиенты), 10% UPDATE |
| **chat_messages** | OLTP + Streaming | 90% INSERT, 10% SELECT (история чата) |
| **chat_sessions** | OLTP | 60% INSERT, 30% UPDATE, 10% SELECT |
| **sentiment_analysis** | Event Streaming | 99% INSERT, 1% SELECT |
| **recommendations** | OLTP | 50% INSERT, 50% UPDATE (apply/dismiss) |
| **knowledge_base** | OLAP (чтение) | 95% SELECT, 5% UPDATE |
| **company_charter** | Кэш | 99% SELECT (кешируется в Redis) |
| **daily_stats** | OLAP | 100% INSERT (агрегация) |
| **audit_log** | Event Streaming | 100% INSERT |

#### Шаг 3. Требования к консистентности

| Сущность | Требование | Обоснование |
|----------|------------|-------------|
| **clients** | Strong | Данные клиента должны быть точными (email, телефон, статус блокировки) |
| **users, user_roles** | Strong | Права доступа не могут быть рассинхронизированы |
| **chat_messages** | Strong | Клиент должен видеть все сообщения |
| **chat_sessions** | Strong | Статус сессии должен быть точным |
| **recommendations** | Eventual | Не критично, если рекомендация появится на 0.5 сек позже |
| **sentiment_analysis** | Eventual | Может обработаться асинхронно |
| **daily_stats** | Eventual | Отчёты не требуют real-time |
| **audit_log** | Eventual | Запись в лог может быть асинхронной |

#### Шаг 4. Требования к доступности

| Компонент | Требуемая доступность | Обоснование |
|-----------|----------------------|-------------|
| **Приём сообщений** | 99.99% | Клиент не должен видеть ошибки при отправке |

#### Шаг 5. Требования к мутабельности схемы

| Сущность | Мутабельность | Обоснование |
|----------|---------------|-------------|
| **clients** | Низкая | Структура клиента стабильна, но могут добавляться поля (например, доп. почта) |
| **users** | Низкая | Структура пользователя стабильна |
| **chat_messages** | Средняя | Могут добавляться поля (например, reactions) |
| **sentiment_analysis** | Высокая | ML модель может выдавать новые эмоции |

#### Шаг 6. Требования к транзакциям

| Сценарий | Нужна транзакция? | Обоснование |
|----------|-------------------|-------------|
| Создание клиента + первая сессия | Да | Клиент должен быть создан атомарно с сессией |
| Сохранение сообщения + анализ тональности | Да | Либо оба сохранены, либо ни одного |
| Обновление клиента + обновление его сессий | Нет | Можно асинхронно |
| Обновление статуса сессии + запись в лог | Нет | Лог можно записать асинхронно |
| Применение рекомендации + обновление статистики | Нет | Статистика может обновиться позже |

#### Шаг 7. Требования к поиску и запросам

| Тип запроса | Пример | Инструмент |
|-------------|--------|------------|
| **Поиск по ключу** | "Дай клиента по ID" | B-tree index |
| **Поиск по email/телефону** | "Найди клиента по email" | **B-tree уникальный индекс** |
| **Поиск по времени** | "Сообщения за последний час" | B-tree на timestamp |
| **Полнотекстовый поиск** | "Найди сообщения со словом 'доставка'" | **GIN index + to_tsvector** |
| **Поиск по клиентам** | "Найди всех VIP клиентов" | B-tree на segment, GIN на tags |
| **Агрегация** | "Средняя тональность за день" | **TimescaleDB / ClickHouse** |
| **Поиск по JSONB** | "Найди сообщения с device_type = 'mobile'" | **GIN index на JSONB** |
| **Поиск по тегам** | "Сессии с тегом 'urgent'" | **GIN index на array** |
